# Database foundation

The accepted initial `synex_core` Production-Beta profile targets MariaDB `11.8.8` with InnoDB and oxmysql `2.14.1`. The source and migration guards also account for MySQL `8.4` metadata differences, but the repository does not run a MySQL service job and MySQL is outside the initial acceptance target. Other database versions are likewise unaccepted even when the DDL happens to apply. Runtime SQL uses positional `?` parameters only. Named placeholders and cross-resource table access are prohibited.

The database session used by oxmysql must be UTC. Synex deliberately relies on database time for leases, expiries, queues, outboxes, audit timestamps, and retention cutoffs; most persistence uses `CURRENT_TIMESTAMP(6)`, while archive cutoff/copy operations use `UTC_TIMESTAMP(6)`. Before migration bootstrap, Core executes `TIMESTAMPDIFF(SECOND, UTC_TIMESTAMP(), CURRENT_TIMESTAMP())` through the normal persistence adapter and requires an exact zero result. A nonzero result, malformed result, or database error fails boot; `synex doctor` repeats the same check. Synex does not issue a session-time-zone command, and no connection-string parameter is assumed here.

## Migration protocol

Migration files are UTF-8, LF-normalized, forward-only inputs. The Core migration runner computes SHA-256 over LF-normalized bytes and records the digest in `synex_schema_migrations`. An already-applied `(resource_name, migration_id)` whose digest changes is normally a startup error, and repairs require a new migration. The sole registered exception is the exact old-to-current checksum correction for `synex_core:021_worker_queue_scalability`: it is accepted only when the authoritative applied marker contains the published old digest, so the corrected SQL is not executed again. Failed, applying, indeterminate, reversed, differently hashed, or differently named states remain blocked; see [Migration execution](../migrations.md#immutability).

Each top-level statement is separated by a line containing exactly:

```sql
-- synex:statement
```

The runner does not enable multi-statement queries. Every current migration containing DDL is declared `transactional: false`: both MariaDB and MySQL can implicitly commit DDL. A migration may append idempotent `INSERT ... SELECT ... WHERE NOT EXISTS` backfills after its tables; each backfill is its own delimited statement. `synex_cluster_leases` provides a time-bounded lease plus monotonically increasing fencing token. Each execution also owns a row in `synex_schema_migration_fences` containing that exact owner/token pair and its completed statement boundary. Core verifies both records in short transactions before and after each statement, and the marker transaction locks the lease row before it writes the applied record, fence, and attempt state. Database time, never host clock time, determines lease expiry. Lease retention is domain-aware: saga and character-deletion leases receive eligibility in their fenced terminal domain transaction; exact session/admission release retires its held lease; and a separate bounded indexed recovery queue may retire only already-expired marker-`NULL` `session:` or `admission:` rows. Acquire/reacquire clears eligibility atomically before publishing new authority. Unknown, generic, migration, and active leases are never selected merely because they expired. Acquiring terminal durable domain names locks and validates the domain row first and rejects terminal identities, preserving the fencing invariant after compaction.

The migration runner starts an independent lease heartbeat while SQL is in flight. Safety does not depend on that heartbeat winning: an existing `applying`, legacy `failed`, or `indeterminate` fence is never reclaimed automatically, even after lease expiry. A pre-fence attempt in any non-applied state is also blocked as indeterminate rather than retried. This prevents a second Core from running the same migration while the first database statement is still executing. A submitted statement with an uncertain result leaves a terminal operational block (`MIGRATION_INDETERMINATE`); a stale owner cannot write `applied`, `failed`, progress, or attempt markers because every such write is fenced by the current lease and the per-migration owner/token. oxmysql's experimental interactive transaction has a 30-second guard and therefore is not used as a long-lived advisory-lock substitute.

Migration `019` materializes immutable target-instance authority for bounded session-control polling and auditing. Migration `020` replaces terminal-domain joins with an explicit transactional lease-eligibility queue and adds bounded open-character and open-user session indexes. Migration `021` adds the exact saga, outbox, and idempotency response queues consumed by the revised bounded workers and backfills response eligibility. Migration `022` installs database-authoritative idempotency capacity. Migration `023` adds the exact generated session/admission lease discriminator, its bounded expiry-recovery queue, and the stale open-session heartbeat queue. Migrations `024` and `025` add retained session-control and cluster-lease capacity authority; migration `026` adds the exact owner-aware local connection-authority index. Apply `017` through `026` during the same full-stop window before starting new Core code.

Migration `023_lease_authority_recovery.sql` verifies the generated `lease_authority_kind` column by exact normalized expression, type, collation, nullability, and stored-generation metadata; an extra classification branch or different semantics aborts the upgrade. Its `(lease_authority_kind, terminal_compaction_at, expires_at, lease_name)` index bounds alternating expired session/admission recovery, while `(closed_at, last_seen_at, id, server_instance_id)` bounds stale open-session selection. The worker rechecks kind, expiry, and marker under lock before retirement, so a concurrent reacquire that cleared the marker survives.

Migration `014` adds nullable `owner_resource` to legacy saga rows, replaces correlation uniqueness with the owner-scoped `(owner_resource, saga_type, correlation_id)` key, and adds nullable `producer_resource` plus terminal-compaction metadata to the generic Core outbox. New runtime writes require an owner. Existing `NULL` rows are deliberately not attributed to Core: legacy sagas are excluded from owner-scoped recovery, and legacy outbox rows fail closed during dispatch. To remain repeatable on both MariaDB 11.8 and MySQL 8.4, the migration performs metadata-guarded DDL through a temporary stored procedure and removes it afterward; the migration database principal therefore needs `CREATE ROUTINE`, table `ALTER`, `EXECUTE`, and `ALTER ROUTINE` (which authorizes dropping the temporary procedure) for this maintenance step.

Migration `015` is the additive upgrade for character-deletion reconciliation. It adds bounded attempt counters, last/next-attempt timestamps, the active lease fencing token, and the `(state, next_attempt_at, created_at, id)` due-work index. Existing nonterminal plans become due through the column default; the reconciler then advances them with optimistic versions and the current lease token. The migration uses the same temporary metadata-guarded procedure and routine privileges as `014`. Stop pre-`015` Core instances before starting the upgraded runtime so an older unfenced deletion worker cannot overlap the new coordinator. This repository validates the migration statically; operators must still run the gated disposable-schema and restored-copy upgrade tests for their deployed MariaDB/MySQL version.

Migration `021` creates `(state, updated_at, id)` for finite per-state saga keyset cycles, plus distinct `(state, payload_compacted_at, published_at, id)` and `(state, payload_compacted_at, available_at, id)` terminal-outbox queues. The Core idempotency queue uses `(state, response_compaction_at, expires_at, namespace, idempotency_key)`; completion leaves the marker `NULL`, while compaction clears the response and timestamps the marker in the same bounded update. The migration backfills completed rows whose response is already `NULL`, preventing them from remaining an ever-growing ineligible prefix. Every shape is verified against `information_schema` before boot may continue.

Migration `024` adds database-authoritative retained-row quotas for session-control requests and the exact `(state, completed_at, request_id)` terminal queue. Its singleton stores global use plus global/per-requester limits; a second table stores exact all-state counts by `requested_by_instance_id`. Existing use may exceed a limit, so no counter-to-limit check exists and only an absent request is blocked until drain. The full-stop backfill and metadata guard fail on overflow, drift, a non-exact check/FK/index definition, or a mixed writer that bypassed the new counters.

Migration `025` adds database-authoritative retained-row quotas for `synex_cluster_leases`. Its stored generated kind is `NULL` only for the exact `schema_migrations` bootstrap lease; `session`, `admission`, `saga`, `character`, and `other` counters cover every other active or terminal row until deletion. The committed global limit is 1,000,000; kind limits are 500,000 session, 250,000 admission, 250,000 saga, 100,000 character, and 100,000 other rows. Existing use above policy remains valid, while only an absent name is denied until drain or a reviewed raise. The migration fails on unsigned overflow, classifier/counter drift, weakened metadata, or a MySQL named check reported as not enforced. Pre-`025` acquire and compaction writers must not overlap the backfill or upgraded runtime.

Migration `026` installs the exact non-unique BTREE index `(lease_authority_kind, terminal_compaction_at, owner_id, lease_name)` for next-boot local connection-authority recovery. The metadata guard re-verifies the generated authority kind's normalized exact expression and validates all four columns, their order and ascending full-column index entries, plus the terminal-marker, owner, and lease-name definitions. It also capability-detects MariaDB `IGNORED` or MySQL `IS_VISIBLE` metadata, requires all four entries to be optimizer-usable, and executes a harmless runtime-shaped `FORCE INDEX` probe. Cleanup performs separate equality scans for `admission` and `session` inside the exact local instance owner range, caps the combined locked result at the configured connection-authority bound plus one, and updates only the selected `lease_name` primary keys. A final indexed `LIMIT 1 FOR UPDATE` recheck for each kind makes an over-bound or concurrent residual row fail closed and roll back the transaction. Capacity counters are unchanged until later exact terminal compaction deletes a retired row. Local Saga, character-deletion, and `other` leases, foreign owners, and similar owner prefixes are deliberately excluded.

Historical supported-version upgrade certification is scheduled for the post-Beta promotion phase. The initial Core Beta still requires a clean 26-migration schema and fail-closed checksum/fence behavior, but it does not claim a supported upgrade from an earlier public Synex release.

## Ownership boundaries

Core owns users, raw identifiers, sessions, characters, access decisions, fenced migration state, kernel idempotency, the kernel outbox, sagas, deletion plans, append-only audit and its non-destructive archive mirror, cluster-instance boot authority, retained cluster-lease capacity, session-control requests, their requester-boot claims, and their retained-row capacity authority, persistent RBAC, and the reviewed legacy-import journal plus hashed legacy-ID mappings. Raw identifier values are sensitive: they are used only for server-side lookup and DB uniqueness, and must never enter logs, state bags, client payloads, traces, or outbox events.

The experimental `synex_groups` snapshot declares ownership of groups, memberships, grades, grade capability rules, grade assignments, primary-membership pointers/events, read-model versions, immutable membership events, local idempotency records, its local outbox, and an idempotent character-deletion journal. A membership stores an opaque `(subject_kind, subject_ref)`; it does not query Core identity tables.

The experimental `synex_accounts` snapshot declares ownership of currencies, accounts, owner bindings, account-local access roles/grants, operations, ledger transactions, paired postings, reversal links, balance snapshots, audit, outbox, holds, hold events, reconciliation runs, warning findings, the versioned integrity read model, its non-destructive financial transaction archive mirror, and an idempotent character-deletion journal. Owner and principal references are opaque. It does not query group or Core identity tables. Cross-domain existence and authorization are established before calling the service through contracts, never by cross-resource joins.

The `synex_entities` snapshot owns the durable entity registry described below. The repository-wide database harness includes its `001_entities.sql` migration as rework regression coverage; that inclusion is not a Core support claim.

Lifetime-coupled tables use foreign keys inside each owner boundary and deletes default to `RESTRICT`; lifecycle work anonymizes or appends terminal state rather than cascading economic or audit history. The two archive mirrors are intentionally self-contained and have unique source-row identifiers instead of foreign keys, so preserving them never depends on the source row's lifetime.

## Experimental foundation ABI

The current groups and accounts rework snapshots are server-only. Their ABI is experimental, excluded from Core certification, and may change. They currently acquire the kernel facade with:

```lua
local api, err = exports.synex_core:GetAPI('^1.0.0')
```

They register provider discovery through `api.Services.provide` and register every Invoke operation through `api.RPC.registerServer`. Consumers call a separate contract name and version:

```lua
local result, err = exports.synex_core:Invoke(
    'synex.accounts.transfer',
    '1.0.0',
    request,
    options
)
```

Contract names never contain a version suffix. All generated contracts in this checkout use `network: none`, and their providers make no `registerNetwork` registrations. Domain resources deliberately expose no convenience exports: a nested export would cause Core to observe the provider resource instead of the original caller and would destroy the capability boundary. Consumers call `exports.synex_core:Invoke` directly; `options` must never be used to assert or override caller identity. The optional compatibility/control events are separate bounded resource interfaces, not generated domain contracts.

The optional service-discovery surface is read-only and declares a capability for every exposed method. `synex.groups` exposes `get`, `get_read_model`, `list_subject_memberships`, `check_capability`, and `get_control_summary` under `synex.groups.read`. `list_subject_memberships` returns at most 64 active memberships plus an explicit `truncated` flag. `synex.accounts` exposes `get_snapshot`, `list_owner_accounts`, and `get_hold` under `synex.accounts.read`, `get_access` under `synex.accounts.access.read`, and `get_integrity` plus `get_control_summary` under `synex.accounts.integrity.read`. `list_owner_accounts` is the compatibility projection: it returns at most 64 active `cash`/`bank` asset accounts plus `truncated`, not an unbounded general account search. `synex.entities` exposes `getHealth` under `synex.entities.health` and `getControlSummary` under `synex.entities.read`. Mutations in these three domain resources are registered only as server RPC contracts, so they pass through Core's caller identity and capability checks.

Every mutation requires a lowercase UUID `idempotency_key`. A key is bound to the operation name and a canonical request fingerprint. Reuse with the same request returns the stored response; reuse with different input returns `IDEMPOTENCY_CONFLICT`. The idempotency insert, domain changes, immutable audit/outbox event, and stored response commit in one local transaction.

The generic Core coordinator additionally charges every new permanent key to database-authoritative global, owner, and namespace counters in the same interactive transaction as its claim. The lock order is global, owner, namespace, then exact key. Capacity never causes an existing key to execute again: replay, conflict, expired-response, failed, and indeterminate outcomes remain reachable at or above a limit, while only an absent key is denied. Counter rows cover every persisted state and are not derived by repeated runtime `COUNT(*)` scans. See [Operations](../operations.md#idempotency-capacity) for limits, metrics, alerts, and the controlled raise procedure.

Remote duplicate-session control uses a separate retained-row quota. Issuance locks the admission gate, target session and exact pending request, global counter, then requester counters in sorted order. An exact valid pending request remains usable at a limit without a second charge; only absence reserves both counters before inserting the request and requester-boot authority in the same transaction. A stale foreign pending row is terminalized before any capped replacement attempt. Terminal compaction locks deterministic completed/expired candidates, global authority, and requester counters, then deletes the exact child before the terminal/cutoff-rechecked parent and releases both counts. Pending rows never enter that queue. See [Operations](../operations.md#session-control-capacity-and-retention).

Cluster-lease acquisition is also retained-capacity aware. Boot-fenced acquisitions lock requester instance, boot, and any durable domain before the exact lease identity. An absent identity is provisionally claimed with `INSERT IGNORE` while the row is still first in the lock order; a duplicate winner is reread under lock and follows the ordinary same-owner, expired-owner, or `LEASE_BUSY` path without a second charge. Only a newly claimed non-migration name then locks global and kind authority and increments both counters in the same transaction. The exact `schema_migrations` lease bypasses the 025 tables so migration bootstrap remains possible before those tables exist. Terminal compaction locks a bounded ordered batch, global authority, and affected fixed kinds in sorted order, then exact-deletes and decrements every counter atomically. See [Operations](../operations.md#cluster-lease-capacity).

Prepared Core restart sequencing treats the database drain as a prerequisite to owner teardown. The workflow closes the normal database activity gate, drains the mandatory deferral tick, waits for the complete tracked query/transaction count to reach zero, and only then quiesces resource owners and validates scheduler evidence. Its private database control lane becomes available afterward for the current preparation coroutine's durable status, lease, session, and control cleanup. A drain timeout leaves the Core loaded and fail-closed without beginning owner teardown.

At runtime, a separate bounded UTC-session probe controls the database availability fence and gates every ordinary database-backed recurring handler. A returned failure, adapter exception, unavailable watchdog, or fixed five-second watchdog expiry closes player admission; concurrent and later gated database workers suspend, while any pre-existing `UNHEALTHY` worker retains its diagnostic state. The connection heartbeat is deliberately exempt and remains active for pending/session authority cleanup, failing unrenewable authority closed. A normally returned failure completes its tracked activity and retries with 5/10/15-second bounded backoff. After MariaDB returns, one successful probe persists degraded state only; a second consecutive success plus dependency and instance-status reconciliation is required before database work resumes, while independent health reasons can continue blocking admission.

The watchdog does not cancel the driver promise or Lua `Await`. In oxmysql `2.14.1`, pool `getConnection()` can reject without invoking the Lua callback; that single tracked probe then remains outstanding even when a later independent query can reach MariaDB. Core neither discards the activity nor launches superseding probes. Restore and verify MariaDB, then restart the complete FXServer process once so the adapter and Core terminate together. A raw Core restart, an oxmysql-only restart, or a restart loop is not supported.

The accepted profile's final database-outage/recovery run passed: Core reached `DEGRADED` with admission closed in 6.73 seconds, the complete FXServer process stopped, and MariaDB plus a fresh FXServer process reached `READY` in 10.86 seconds. All 26 migrations, attempts, and fences were applied; no nonterminal migration, open session/authority, Saga, outbox, or idempotency work remained, and probe replay was idempotent. Full backup/restore certification, historical upgrade rehearsal, and a long soak are post-Beta promotion work; none changes the runtime's fail-closed database semantics described above.

Entity persistence also uses the caller-bound Core API, but its lifecycle, service health, and generation-token rules are documented separately in [Entity authority](entities.md).

## Concurrency and retries

The Core transaction model and experimental account snapshot expect oxmysql `READ COMMITTED` (`mysql_transaction_isolation_level 2`); Synex does not set that operator ConVar. `synex doctor` reports the current Cfx ConVar expected by the adapter. Set it before oxmysql starts and restart the adapter after any change; that report does not prove what an existing pooled connection previously applied. It also deliberately does not label a query on an arbitrary pooled or independent session as proof of the active transaction: oxmysql applies `SET TRANSACTION ISOLATION LEVEL` when establishing its transaction path, while session-variable reporting has different next-transaction semantics across the database engines considered by the source. Verify the Doctor result and the exact deployed adapter/database pair. The account rework snapshot uses explicit `SELECT ... FOR UPDATE`, sorts both public IDs, and acquires each account row and latest-snapshot row through separate statements in that ascending order. Writes use optimistic versions or unique sequence constraints as a second line of defense.

Deadlocks remain normal under concurrency. Core batch and interactive transaction wrappers recognize error `1213`, SQLSTATE `40001`, or a deadlock diagnostic and retry up to `database.deadlockRetries` with a bounded wait (two retries by default, five at most). After exhaustion the error remains retryable; any caller-level replay must use the original idempotency key and exact request. Do not retry validation errors, authorization failures, insufficient funds, terminal holds, or idempotency conflicts. A network failure after commit is resolved by replaying the same idempotency key.

Outbox delivery is at least once. The Core, groups, and accounts dispatchers claim ready rows in short transactions, publish outside the claim transaction, and mark success afterward. The groups and accounts workers run once per second with batches of at most 25 and use the capability-gated Core `Events.publishOutbox` path. Generic Core outbox rows preserve their original `producer_resource`; dispatch uses that resource's current epoch and manifest event authority, never Core authority. Consumers deduplicate on the 36-character `event_id`. Attempts use bounded exponential backoff; the tenth failed attempt becomes `dead` and retains `last_error_code` for operator review. The bounded Core retention worker later uses separate published/dead range indexes under one fairly rotated batch budget, replaces only terminal payload/header JSON after the configured windows, retains identity and failure metadata, and records `payload_compacted_at`; pending/publishing rows are excluded. Domain writes never publish directly.

## Retention archive mirrors

The committed retention policy defaults both `audit` and `financial` to `retain_forever`, so no archive worker is scheduled by default. In `archive` mode, Core schedules `core.retention.audit_archive`. The experimental accounts snapshot can schedule `synex_accounts.retention.financial_archive` at the configured `workerIntervalMs`, but that path is outside Core Production-Beta support. The Core audit worker locks at most `batchSize` rows from its indexed unrecorded queue, mirrors them with UTC database time, and records the matching archive timestamp on the source row in the same transaction. The accounts snapshot mirror remains an idempotent, UTC-based bounded insert.

`synex_audit_archive` mirrors eligible rows from `synex_audit_log`; `synex_financial_transaction_archive` stores a self-contained projection of eligible ledger transactions, their unique posting, operation, currency, and account public IDs. Unique source-row keys make repeated batches safe. Core changes only `synex_audit_log.archive_recorded_at` after the matching immutable mirror row exists; it never rewrites audit evidence or deletes a source row. Financial archiving does not mutate or delete transaction, posting, snapshot, operation, or account history. There is no purge command or public deletion service; archive storage, access control, backup, and any separately approved destruction workflow remain operator responsibilities.

Session-control coordination has an intentionally different lifecycle. Completed and expired rows become eligible for hard deletion only after `retention.sessionControlAfterDays`; a fair bounded worker processes their separate indexed queues. An elapsed `expires_at` never makes a pending request deletable, and authority maintenance must first set a deterministic terminal state and `completed_at`. Request and child-authority rows are ephemeral after the grace, not audit history, and their generated IDs are never reused.

## Experimental account snapshot invariants

All amounts are integer minor units in the range `1..9007199254740991`. Floating-point amounts are rejected.

| Invariant | Enforcement |
| --- | --- |
| No mutable balance on `synex_accounts` | Booked and reserved values exist only in append-only `synex_account_balance_snapshots`. |
| Every value movement has two sides | One `synex_ledger_postings` row names a distinct debit account and credit account. |
| Debit equals credit | `debit_minor > 0` and `debit_minor = credit_minor` are DB checks; one paired posting is unique per ledger transaction. |
| Currency cannot cross | Transaction creation joins both accounts on the same `currency_id`. |
| Available funds cannot be overspent | The locked latest snapshot must satisfy `booked_minor - reserved_minor >= amount_minor`. |
| Mint and burn are explicit | Mint requires `mint -> asset`; burn requires `asset -> burn`. Only a system-owned mint account may be negative. |
| Audit and event are atomic | Ledger, snapshots, `synex_account_audit`, local outbox, and idempotent response share one transaction. |
| Reversal never edits history | `synex.accounts.reverse` appends one inverse posting and a unique `synex_ledger_reversals` link; neither the original nor its reversal may be reversed again. |

In this API, the debit account is the value source whose booked amount decreases; the credit account is the destination whose booked amount increases. This naming is a game-economy transfer convention, not a general-purpose GAAP chart-of-accounts implementation.

A hold does not move booked value. Creation appends a snapshot that increases `reserved_minor`, reducing available value. Release appends a snapshot that removes the reservation. Capture is the only hold transition that moves booked value and therefore must create a balanced ledger transaction. `synex_account_hold_events` allows one creation event and at most one terminal event, so capture and release cannot both succeed.

Account-local access uses immutable role definitions plus versioned grants. A role contains a unique subset of exactly these permission keys: `view`, `deposit`, `withdraw`, `transfer`, `history`, `manage`, and `close`. At most one active grant exists for an account/principal tuple; revocation clears the active marker and appends audit/outbox records. The owner receives an `owner` role and grant when the account is created, and migration `004_access_integrity.sql` idempotently backfills that role, all seven permissions, and an owner grant for pre-existing accounts. These grants are domain facts, not caller identity: a server-local caller must resolve the authoritative user/character/group in its own server-side domain and query `synex.accounts.get_access`. Request fields may never assert that identity.

`synex.accounts.run_reconciliation` advances a per-currency model version and writes an immutable run plus zero to five findings. Rules cover debit/credit imbalance, aggregate snapshot drift, negative asset snapshots, reservations exceeding booked value, and orphan transactions. Every finding is severity `warn`; reconciliation only records audit/outbox evidence and never bans a principal, mutates ledger history, or repairs balances. Aggregate `BIGINT` counts and `DECIMAL(36,0)` totals are returned as decimal strings to avoid Lua/JSON safe-integer loss.

Group capability evaluation accepts exact rules and trailing segment wildcards such as `synex.accounts.*`. Any matching `deny` wins over every matching `allow`. Primary membership is a separate per-subject pointer: selecting a new primary never removes the subject's other memberships. Every grade, membership, capability, and primary change increments the affected `synex_group_read_model_versions.model_version`; consumers use that version as the cache invalidation token.

Snapshots, ledger rows, membership events, audit entries, and saga steps are append-only. APIs return defensive copies; callers cannot mutate persisted history by changing a returned Lua table.

## Character deletion and durable access policy

Access bans and allowlist entries are relational durable records. The schema can target exactly one user or identifier, supports expiry and revocation, and is queried by the server-side connection pipeline. The current public `api.Access` mutation/list surface and console commands are user-ID scoped; they do not expose identifier-target creation. Resource mutations require `synex.access.manage` plus a bounded idempotency key and commit the access change with before/after audit evidence. Listing requires `synex.access.read` and returns at most 64 bans and 64 allowlist rows for one user, each with an explicit truncation flag. Neither capability is granted by default. JSON configuration is not a replacement for these records.

`synex_character_deletion_plans` coordinates owner-specific character cleanup. `plan_json` may contain only bounded resource owner and action metadata; it must never contain SQL. The coordinator validates the stored plan against the relational `character_id`, processes only rows whose `next_attempt_at` is due, and combines optimistic `version` transitions with the active lease fencing token. Lease contention before an attempt moves that row out of the immediate due set, so a busy queue head cannot indefinitely hide later work. Plans and append-only audit remain after completion or failure.

Boot-fenced lease acquisition locks the ready instance, exact boot row, durable domain when present, and exact lease identity in that order. An absent identity is provisionally claimed with `INSERT IGNORE`; only its winner reserves global and fixed-kind capacity before the locked final reread. A duplicate contender rereads the winner and follows existing-name semantics without a second charge. A valid foreign owner is never replaced; every successful same-owner reacquisition advances the fencing token. Saga and character-deletion workers use a new owner for each acquisition so a parallel attempt receives `LEASE_BUSY` instead of sharing a logical worker identity. Session creation locks the same instance, boot, and lease authority in the transaction that inserts the session, serializing it against restart registration and cleanup.

The current experimental lifecycle participants are explicit snapshot behavior. `synex_accounts` blocks deletion while a character-owned account has a nonterminal hold; during idempotent `deleteCommit` reconciliation it closes and anonymizes the character's owned accounts, revokes affected active grants, and retains ledger history in one domain transaction. `synex_groups` replaces character subject references with a generated anonymous reference and invalidates affected read models while retaining event history. `synex_entities` deletes runtime-temporary entities and retains persistent records under a generated retained owner reference. Each `deleteCommit` receives the compatible plan envelope with exactly one bounded action: the action prepared for that participant's resource. Actions belonging to other resources are not disclosed. None of these participant implementations is part of Core Production-Beta certification.

## Database test gate

`npm run test:database` always runs static checksum, delimiter, ownership, Lua parse, and ledger-invariant tests. The live suite is skipped unless both variables are present:

```text
SYNEX_TEST_DATABASE_LIVE=1
SYNEX_TEST_DATABASE_URL=mysql://user:password@host:3306/synex_test_local
```

The database name must match `synex_test_[a-z0-9_]+`. The harness applies project-owned statements one at a time with multi-statements disabled, inspects InnoDB/check/FK metadata, verifies all-state idempotency, session-control, and cluster-lease quota backfills plus malicious constraint/classifier/check-enforcement rejection, and verifies migration `026`'s exact owner-aware index, optimizer visibility, and forced-query usability. It then runs real parallel counter-direction transfers, duplicate idempotency, READ-COMMITTED same-name lease races, and bounded local connection-authority recovery on independent connections, including unrelated-kind isolation, exact selected-name retirement, over-bound rollback, and residual-phantom rollback. It verifies balanced ledger rows, immutable snapshot sequencing, reconstructed/nonnegative balances, atomic audit/outbox counts, and single-charge cluster-lease fencing. It does not create or drop a database and leaves schema cleanup to the test operator. Never point the gate at production or a shared development schema.
